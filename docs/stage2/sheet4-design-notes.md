## 2. Architecture

### 2.1 Data path

    RP2040 PL022 ──SCK/MOSI/CS_N──> J401 ─> U401 (B→A) ─> FPGA pins 5/3/2
      ┌──────────── SCK domain ────────────┐   ┌────────────────── clk_core (50 MHz) ──────────────────┐
      │ z2_spi_slave RX: shift MOSI, one    │   │ z2_hostif: pop 1 entry/clock → parser (SYNC, CMD,     │
      │ byte → {dropped, start, byte} ─────────>│ SEQ, LEN, CRC) → 512 B staging EBR → validate V1–V5 → │
      │ (CS_N high = async reset)  z2_afifo │   │ executor → host port H-1..H-6 → z2_lbus (SRAM) /      │
      │                             16 × 10 │   │ z2_mbx (registers) → response builder → 512 B EBR     │
      │ z2_spi_slave TX: byte 0 = static    │<──────── response RAM (written only while executing)   │
      │ register; bytes 1.. one ahead ──────┘   │ ATTN = idle & CS_N high; STATUS counters               │
      └─────────────────────────────────────┘   └───────────────────────────────────────────────────────┘
    FPGA pin 4 MISO, pin 6 ATTN, pin 1 IRQ_N ─> U402 (A→B; /OE from U405: GP24 > 0.93 × header 3.3 V) ─> R411–R413 ─> J401 ─> RP2040

**Resources (LCMXO2-4000HC, z2_top):**
- 1090 slices (50 %), 2150 LUT4, 974 registers;
- 2 EBR (DP8KC 512 × 8: staging and response);
- PIO: 90 + 4 JTAG of 115.

The host-link engine is about 461 FF / 866 LUT4. That is why the design no longer fits the 2000HC; **C-30 (approved) adopts the 4000HC.**

### 2.2 Protocol in one paragraph

The normative text is [../hdl/host-link-protocol.md](../hdl/host-link-protocol.md).
- **Command frame:** SYNC, CMD, SEQ, LEN (big-endian), payload, CRC-16.
- **Response:** read later with GET_RESPONSE, after ATTN rises: RSYNC, STATUS, SEQ, RCODE, LEN, payload, CRC.
- **Commands:** IDENTIFY, STATUS, GET_RESPONSE, RESET_LINK, ECHO, SRAM_WRITE/READ (≤ 128 words), SRAM_WRITE_BE, REG_WRITE/READ.
- **Re-sending is safe:** commands are repeatable and GET_RESPONSE has no side effects. A master can resend after any timeout or CRC error.

### 2.3 Clock-domain crossings

| Crossing | Mechanism | Safety argument |
|---|---|---|
| MOSI bytes, SCK → clk_core | z2_afifo: Gray pointers, two-flop synchronisers | Formal fv_afifo (requirement 5) |
| CS_N → clk_core | Two-flop synchroniser (`cs1`, `cs2`); frame end = CS_N high **and** FIFO empty for 4 clocks | The last byte is written on its 8th SCK↑, at least tCSH = 100 ns before CS_N rises (protocol §2), and its pointer crosses within 3 clocks |
| Response RAM and byte 0, clk_core → SCK | Written only while executing an accepted command; RSYNC (byte 0) written last; read by the SCK domain | **Protocol invariant:** the master clocks a GET_RESPONSE only after ATTN = 1, and ATTN is low throughout execution. A frame clocked during execution (busy) reads stale or partial data, and its RSYNC/CRC check fails (byte 0 is RSYNC only when complete) |
| ATTN, IRQ_N, STATUS → RP2040 | Registered in clk_core; sampled by firmware | Level signals, no timing relation to SCK |
| CS_N as asynchronous reset of the SCK-domain frame registers | Asserted at any time; released ≥ 100 ns before the first SCK↑ (tCSS) | Excluded from STA (`BLOCK RESETPATHS`); design rule exercised with random tCSS in tb_spi P15 |

`BLOCK INTERCLOCKDOMAIN PATHS` in the LPF stops Diamond from timing these crossings as synchronous paths. Every crossing is one of the above.

### 2.4 Resets

- POR resets both domains. The engine first builds a power-on IDENTIFY response with SEQ 0xFF, then raises ATTN.
- An FPGA reload during a frame or a command loses that frame. A write in flight may leave one word undefined (H-5); the RP2040 quiesces the host port before a JTAG reload.
- An Amiga reset (/BUSRST) does not touch the link (protocol §11).

## 3. Buffer sizing (requirement 2)

Summarised in §1, row 2; full table in protocol §9. The sizing does not depend on the Zorro side:
- the FIFO only has to absorb the pointer-synchroniser latency;
- the staging buffer holds one whole frame;
- the response buffer holds one whole response.

Execution time, which a busy Zorro bus can stretch, never queues SPI bytes, because the master waits for ATTN.

### 5.3 The timing changes and why each is exact

| Change | Exactness | Evidence |
|---|---|---|
| z2_mbx producer check: `q ≤ d ≤ QDEPTH` with `d = nv − c`, `q = p − c` (two parallel subtractions) instead of `nv − p ≤ QDEPTH − (p − c)` (two in series) | Identical whenever M1 holds (0 ≤ p − c ≤ QDEPTH). Where M1 fails, which is unreachable, the new form rejects | Exhaustive comparison over every (nv, p, c) for every queue depth 2¹–2⁷: 0 differences under M1, never accepts more; M1 proven |
| z2_mbx flags: `ne = (p ≠ c)`, `full = ne ∧ (low bits equal)` instead of a subtraction | Identical under M1 | Exhaustive check, every depth; **formal M6** compares them with the occupancy definitions |
| QCTL link-reset magic decoded at the source and registered with the strobe (`zr_magic` in z2_core, `h_magic` in z2_hostif) | The strobe and its data are registered together, so the flag describes exactly the write it accompanies | **Formal M7** (Zorro side, every write); card_model check (host side, every SPI simulation) |
| z2_hostif argument check over two extra clocks (X_PRE, X_PRE2) | Pure pipelining of a decision taken before any transaction | tb_spi P8 (every argument error) |
| z2_hostif read data registered at `h_ack`; status inputs registered | One clock later in the response; content identical. STATUS bits are levels | tb_spi P1, P2, P11; tb_shm via SPI |
| z2_hostif `p_lt7` register for `pb < p_end7` | `pb` steps by exactly one per byte, and `p_end7` (≥ 7) is fixed at `pb = 4`, so the flag falls exactly when `pb + 1` reaches it | card_model check at every clock |

### 6.2 Translators

Four TI SN74AVC4T774PWR [V S66].
- **Pinout** from the PW application figure: 1 DIR1, 2 DIR2, 3–6 A1–A4, 7 DIR3, 8 DIR4, 9 /OE, 10 GND, 11–14 B4–B1, 15 VCCB, 16 VCCA.
- **Function table:** /OE low with DIR high = A→B; DIR low = B→A; /OE high = both ports Hi-Z.
- **VCC isolation:** both ports are Hi-Z if either supply is at GND.
- **Ioff:** ≤ ±1 µA.
- **Input thresholds:** VIH ≥ 2.0 V and VIL ≤ 0.8 V at VCCI 2.7–3.6 V.
- **Unused data inputs** must be held at VCCI or GND (§5.3 note 3).

|---|---|---|---|---|

**/OE tied to GND (U401, U404):**
- TI's typical application allows it: "OE inputs may also be tied to GND to keep device enabled".
- TI recommends a pull-up only where outputs must stay Hi-Z while a supply ramps [V S66 §8].
- Here a ramp can only produce glitches:
  - U401: on FPGA inputs during an X4 power ramp. The result is a garbage frame, rejected by SYNC, length or CRC, and ignored before IDENTIFY anyway;
  - (U402 is not tied: its /OE follows TI's recommendation, pulled up to VCCA and enabled only by U405);
  - U404: LED flicker.
- No glitch can back-power anything, because every output swings within its own VCC (§7).

### 6.3 Decision S4-6: isolating the outputs toward the RP2040 (revision A1)

**Finding** (X4 schematic sheet 21, rendered and read [V S1]):
- The RP2040's I/O supply (IOVDD1–6) and core-regulator input (VREG_VIN) are **P3V_RP**. It is switched from the header's **P3V3_S** by a P-MOSFET, **Q32 (CJ3139K)**, decoupled by about 10.5 µF. Only USB_VDD is elsewhere, on the always-on P3V3_A through R304.
- The X4's **K4** key turns Q32 off through Q33. Q32 has no gate-source pull-up.
- The design must therefore tolerate **the header 3.3 V up while the RP2040's I/O supply is off or collapsing**.

**Requirement (approved):** every FPGA → RP2040 signal isolated whenever the RP2040's I/O supply is unavailable, without relying on an operating rule.

**Revision A1 circuit** (full analysis, options and bounds in [sheet4-s46-isolation.md](sheet4-s46-isolation.md)):
1. **Every carrier → RP2040 output is on U402.** MISO moved from U401 and TDO from U403, as in revision A.
2. **U402's /OE (RP_EN_N) comes from comparator U405** (TI TLV7021, supplied from X4_3V3_REF):
   - U405 compares GP24 (through R426) with 0.930 × X4_3V3_REF (R427 7.5 kΩ / R428 100 kΩ);
   - while GP24 is above the reference, its open-drain output pulls /OE low and U402 drives;
   - otherwise R429 holds /OE at VCCA and U402 is Hi-Z. That covers the RP2040 unpowered, browning out after K4, in reset or BOOTSEL, or firmware not started. R430 holds GP24 low when nothing drives it, and U405's power-on reset keeps its output off.
3. **U402's VCCB is back on X4_3V3_REF.** Revision A's RP_VIO, R416 and R417 are removed.
4. **B-side 100 kΩ pull-downs on every RP2040 → carrier input** (R418–R423, plus the C-26 LED pull-downs), unchanged.
5. **RP2040-side defaults while U402 is disabled with the RP2040 running** (carrier off and the X4 on its own 12 V, a normal state):
   - R424 10 kΩ from **GP24** to X4_GP22_IRQ_N reads "no interrupt";
   - R425 100 kΩ to GND reads "not ready".

**Why it is safe:**
- During K4, GP24 follows IOVDD down. U402 is disabled when GP24 crosses 0.929–0.932 × P3V3_S (± 22 mV for offset and hysteresis).
- At that moment no output is more than **0.29 V above IOVDD**: within VIH max (+0.3 V) and the absolute maximum (+0.5 V) [V S65]. This holds for any discharge rate; only the ≤ 2 µs disable latency matters.
- **GP24 sources ≤ 0.36 mA** and charges no capacitor.

**Revision A** (U402 VCCB = GP24 through R416, C404, R417) was withdrawn after the analysis you asked for:
- C404 holds RP_VIO up after the RP2040 browns out. The RP2040's ESD diodes then clamp it about 0.6 V above the collapsing IOVDD for 0.7–7.4 ms, beyond the pin's absolute maximum.
- Charging C404 at turn-on needs 31–49 mA from GP24 [E].

**Cost:**
- one RP2040 GPIO (GP24);
- one TLV7021 (BOM item 45);
- R424–R430 and C409 (12 passive parts);
- firmware rule FW-1 (§9).

U402's delay is the original 3.3 V-column figure; the timing budget is unchanged.

**C-29 (back-powering through FPGA input clamps), sheet 4 share:**
- Every FPGA input from the X4 domain comes from a translator A output.
- The A outputs are Hi-Z whenever +3V3 (VCCA) is off.
- The carrier-side pull-ups go to +3V3 itself.

So no FPGA input is driven while +3V3 is off. **R-49 stays Open** for sheets 5–6 (debug header, X4 sense lines).

**R-51 (default resistors), sheet 4 share:** RP_IRQ_N, RP_ATTN and RP_MISO have their defaults (R404–R406). **R-51 stays Open** for X4_PWR_EN (sheet 5) and DBG0–3 (sheet 6).

**`PULLMODE=NONE` on all six host-link pins (LPF):**
- It is required, not cosmetic. Diamond's default for an unconstrained pin is PULL:DOWN (the pad report shows it).
- On RP_CS_N, a 30–305 µA pull-down [V S49] against R401 (10 kΩ) can pull the pin to 0.25 V while the X4 is off: a permanently asserted CS_N.

**One accepted artefact.** During FPGA configuration, CS_N can still read low: the weak pull-down is active until user mode, against R401, with the X4 off. A configuration with the X4 off may therefore count one frame error at start-up. Firmware clears the counters with RESET_LINK after IDENTIFY (§9).
